Flags below are about what those numbers do and do not prove.

1. The headline speedup is measured against the wrong baseline for the PR that was built. Rows "ran the issue's benchmark on 65d1cd9c unchanged" and "ran the editor benchmark on the hardened branch alone" compare 2990ms -> 1381ms, but the PR branch (wm/1737-produce-block-pr) sits on 9a5f9307, which already has the early Schema exports. The issue says that commit gets hover to about 533ms. No editor benchmark was run on the PR tip 20f29c483 or on 9a5f9307 (the transcript shows only five profile-block-language-service runs, none in wt-pr). The commit 33fc89bc2 switches Ui's `uiPages` back to `UiBlock.Model`, so the claim the PR depends on, that this is as fast as the retained workaround, was never measured. Check: run the profiler on 9a5f9307 and on 20f29c483, serially. Rows "PR-shaped branch ready" and "reviewed the core diff myself" do not cover this.

2. The 1288ms comparison is not like for like. Rows "moved produceBlock to the Definition" (1312ms, "about the producer prototype's 1288ms") and the 10:32 message take 1288 from the issue (two samples, different machine and protocol). The issue itself says not to compare absolute times across protocols. The trail row states no caveat. The explanation for the Composition-vs-Definition gap ("typing the Composition's child registrations") was a guess, confirmed by a single before/after pair. The text also guessed that the remaining 1.3s comes from "the other nine child Blocks". That was never measured or followed up.

3. The authoring shape changed from what the user was shown and from what the issue owners asked for. At 10:17 and 10:32 the user was told the cost is "one wrapper call, no private producer, no annotation". The delivered form needs a named `const assembleUiBlock = () => ...` plus a method choice (`produceBlock` or `produceViewlessBlock`). The issue's rejected producer was described as "private producer, explicit annotation, four shape-specific interfaces". The new shape keeps the private producer. It is recorded only in the row "implementation finished: named producer because NoInfer missed the 0.5% rule". Challenge the decision: the 0.5% bar was self-set in the brief (it is in the 12:46 agent prompt, so it was fixed before measuring). The noise floor is 0.2%, and the miss is 0.78% (about 0.2s of full check). That tradeoff gave up the one-line form, and the user should decide it. NoInfer (13 return types) was also never measured in the editor latency benchmark.

4. The "named producer" rule is now only prose. The named-block-producer lint, oxlint recognition of `produceBlock`, the codemod and the docs snippet are all left undone (impl/report.md, deviations.md #1). An inline producer silently costs about +2.2M instantiations (+8.5%) and about +1s on every full Website typecheck. The only guard is the produced-composition-8 fixture (mutation check in impl/perf-mutation-inline.txt: 1,253,018 vs 625,053, which does fail). Nothing guards a consumer's own Block. This is the "two ways to do one task" red flag the assistant itself named at 11:52, and rubric item 4 asked for no lasting second way. The synthesis row "picked candidate 1 as base" does not mention that this was left open.
